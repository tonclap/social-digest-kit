# Обзор соцсетей

Дайджест по отобранному кругу людей. Не вся лента — только те, кого владелец
разметил важностью, и только когда по ним подошёл срок проверки.

> Это шаблон. Подставьте свои пути, свой набор сетей и свои правила приватности
> (раздел «Чего не делать»). Всё остальное — механика, она переносится как есть.

## Где что лежит

- **База:** `social.db` (SQLite), единственный источник правды.
  `people` — люди с `importance` 0–5, `circle`, `bio_summary`, `is_deceased`;
  `accounts` — их профили по сетям, `is_dead` исключает аккаунт из проверок
  (любая причина: удалён, недоступен, закрыт); `observations` — журнал проверок
  (кого, когда, нашли ли пост, `access_blocked` — отдельно от `found_post`);
  `digest_items` — что уже попадало в прошлые обзоры, вместе с `post_url`/`post_date`.
- **Отчёты:** `digest/YYYY-MM-DD.md`.
- **Скрипты:** `scripts/`. **Страницы-прогонщики:** `tools/`.

Работать из корня проекта — пути в командах относительные.

## Ключевое ограничение

**Залогиненного доступа к соцсетям у сессии нет.** VK API требует токен владельца,
FB и IG — его же авторизованный браузер. Поэтому VK собирается через HTML-страницу,
которую владелец открывает у себя, а FB и IG — через браузерный агент. Никакого
фонового сбора «пока ноут спит» не бывает: без владельца за компьютером прогон
невозможен. Это не недоделка, а следствие того, что соцсети закрыты для серверов.

## Порядок

### 1. Кто сегодня к проверке

```
python scripts/due_today.py social.db
```

Печатает: важность, имя, сети, когда последний раз писал и когда проверяли.
Частота считается из важности и активности — человек с важностью 5, который
пишет регулярно, попадает сюда каждый день; он же, замолчавший на полгода, —
раз в две недели. Расписание считается **по каждой сети отдельно**: свежая
проверка VK не «освежает» дату проверки его FB.

Пустой список — нормальный результат: всех уже проверили сегодня. Так и сказать,
не выдумывать работу.

### 2. VK

```
python scripts/export_vk_daily.py social.db tools/vk_daily.html --days 7
```

Печёт страницу с зашитым списком сегодняшних людей. Отдать её владельцу: он
открывает, берёт свежий токен по ссылке на самой странице (живёт сутки), вставляет
сниппет в консоль и через минуту получает `vk_daily_ГГГГ-ММ-ДД.json`. Дождаться,
пока положит файл в папку.

```
python scripts/import_daily.py vk_daily_ГГГГ-ММ-ДД.json social.db --apply
```

Пишет наблюдения в базу и печатает материал для дайджеста. Посты, которые уже
фигурировали как `post_url` последнего наблюдения по этому каналу, отсеиваются —
но это ловит повтор ОДНОГО поста и не гарантирует полноту при нескольких постах
в окне. Окончательная проверка — шаг 5, его нельзя пропускать.

### 3. Facebook и Instagram

API нет. Взять из шага 1 тех, у кого есть `facebook` или `instagram`, и обойти
профили браузерным агентом: открыть страницу, прочитать верхние посты, снять текст
и дату. **Между переходами держать паузу в несколько секунд** — частый обход
профилей это ровно то, за что Meta показывает капчу.

**Сторис в Instagram не открывать.** Их просмотр видно автору, и ежедневный обход
оставит заметный след. Если сторис есть — упомянуть в отчёте, но не смотреть.

Если сеть не собралась — капча, требование подтвердить вход, зависшая лента —
прогон по ней прекращается, и в отчёт идёт честная строка «IG не собран», а не
тихий пропуск.

Записывать наблюдения через `scripts/record_browser_observations.py items.json
social.db`, не разовым SQL — иначе молча теряются две вещи:

- `summary` обязателен ВСЕГДА, даже когда `found_post=0`. Профиль не открылся —
  так и написать, плюс `access_blocked: true`. Это отдельно от «открылся, но
  постов нет».
- `post_url` — если удалось достать ссылку на конкретный пост. Best-effort: не
  тратить лишние клики ради риска капчи, поле необязательное.

### 4. Написать дайджест

`digest/YYYY-MM-DD.md`, прозой. Четыре блока по убыванию срочности:

```
# Обзор соцсетей за 01.08.2026

Собрано: VK ✓ · FB ✓ · IG ✗ (требуется подтверждение входа)
Проверено 27 человек, содержательных постов 9.

## Поводы написать
Только то, у чего короткий срок годности: поздравления, просьбы о помощи, острые
ситуации, дни рождения на этой неделе. Пустой блок лучше натянутого.

## Темы дня
Сюжеты, всплывшие у нескольких человек сразу, или заметные события.

## По людям
Сгруппировать по `circle`, внутри — по важности. На каждого: пересказ в один-два
абзаца и ссылка на пост.

## Не вошло
Репосты без своих слов, реклама, посты без текста. Обязательный блок — чтобы было
видно, что ничего не выброшено молча.
```

Пересказ должен быть самодостаточным: понятно, о чём речь, без открывания ссылки.

Если в посте всплыл **долгоживущий биографический факт** (профессия, место работы,
вуз, творческий проект — то, что не устареет через неделю, в отличие от «съездил
на Байкал») — дописать его в `people.bio_summary` и проставить `bio_updated_at`.
Иначе факт остаётся в одноразовом markdown-файле и теряется для будущих запросов
о человеке.

### 5. Проверить полноту И повторы (обязательно, перед отправкой)

Собрать JSON строк вида

```json
{"person_id":123,"networks":"vk","category":"povod","summary":"одна фраза сути",
 "post_url":"https://vk.com/wall...","post_date":"2026-08-20"}
```

(категории `povod` / `tema` / `po_lyudyam` / `ne_voshlo`) — это тот же файл, что
пойдёт в шаг 7. Прогнать:

```
python scripts/check_digest_completeness.py social.db items.json --date ГГГГ-ММ-ДД
```

Две проверки за один прогон:

1. **Полнота** — каждая находка (`found_post=1`) обязана быть учтена хоть где-то,
   иначе выпадает молча.
2. **Повторы** — среди `po_lyudyam`/`tema` ищет те, у которых пост не изменился
   с предыдущей проверки того же канала (по `post_url`, а без него — по
   `post_date`), и требует перенести их в «Не вошло». `povod` намеренно исключён:
   повод может законно повторяться, пока не решится.

Пустой вывод по обеим, код 0 — можно отправлять. Иначе по каждой строке решить:
содержательная находка, которую забыли пересказать — дописать в «По людям»;
репост/реклама/устаревшее/повтор — дописать строку в «Не вошло». Добавить запись
в `items.json` и прогнать снова, пока оба списка не опустеют.

**Не пропускать этот шаг ради экономии времени.** Именно он ловит настоящие
пропуски — и он же однажды показал, что 11 из 15 «находок» одного дайджеста были
повторами, пересказанными как новые.

### 6. Отдать дайджест владельцу

Файл уже на диске. Сказать путь и коротко пересказать главное в чате — только
после того, как шаг 5 прошёл чисто. Пункты, требующие действия («поздравить»,
«дочитать», «написать»), стоит вести отдельным накопительным списком поверх
дайджестов — иначе повод из блока «Поводы написать» живёт один день и теряется.

### 7. Записать состав дайджеста

```
python scripts/record_digest.py items.json social.db
```

Без этого шага завтрашний прогон перескажет то же самое заново.

## Чего не делать

- Не выдумывать посты и не пересказывать по заголовку. Текст не прочитан — так и
  написать.
- Не открывать сторис в Instagram без явной просьбы владельца.
- Не менять важность в базе от своего имени: `importance` ставит только владелец
  через очередь разметки. Предложить изменить — словами, в конце отчёта.
- Не молчать про несобранное. Строка «Собрано:» с честным статусом по каждой сети
  обязательна: иначе сломанный сбор выглядит как «сегодня никто ничего не написал».
- Не писать наблюдения по FB/IG разовым SQL в обход `record_browser_observations.py`.
- **Не указывать текущую страну, город проживания и местонахождение человека** —
  ни в `people.bio_summary`, ни в тексте дайджеста, ни в `digest_items.summary`,
  даже если человек сам публично об этом написал. Пересказывая пост с топонимом
  (подпись к фото с геометкой, «уехал в X»), передавать содержание **без**
  топонима, а не смягчать формулировку. Исключение — место разового публичного
  мероприятия, которое человек сам анонсирует (концерт, встреча): это не место
  жительства. Сомневаешься — убрать.

  Это не формальность: именно эта строка отделяет дайджест от досье. Без неё
  архив за полгода превращается в карту перемещений полусотни людей, которые
  на такое не подписывались. Родной город, город школы или вуза и прошлые места
  работы — оставлять можно, они не говорят, где человек сейчас.

## Полезное

Просьба проверить конкретного человека вне расписания — найти его в базе по имени
и обойти его сети напрямую, не гоняя весь прогон.

Если в дайджесте несколько дней подряд одни поздравления и репосты — это сигнал,
что круг подобран неудачно. Сказать об этом прямо и предложить пересмотреть
важность у тех, кто стабильно не даёт содержания.

`scripts/mark_deceased.py <db> <person_id> "<note>" --apply` — пометить человека
умершим (не редактировать `is_dead`/`is_deceased` вручную SQL: скрипт ставит всё
сразу правильно).
